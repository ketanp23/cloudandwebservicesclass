Reference

Reading primer

A five-minute refresher on the ideas you'll use. Skim it now; come back to any part during the rounds.

1 · Cloud Adoption Framework (CAF)

A company-wide playbook that turns "we use cloud" into a governed programme. Read it as a lifecycle — Strategy → Plan → Ready → Adopt → Govern → Manage — and remember it's mostly about people and governance, not technology. "Ready" builds a landing zone: a pre-secured, pre-governed plot of cloud with the rules baked in before any workload lands.

2 · Hybrid environments

Running some systems in the cloud and some in your own data centre, joined by a secure link so it behaves as one. Companies stay hybrid on purpose — for regulation, legacy systems, latency (things that must be physically close), and data gravity (data too big to move). The hard part is keeping one identity and one view across both sides.

3 · Scaling & multi-environment

  • Scale up (bigger server) vs scale out (more servers). Web tiers scale out; databases are the usual bottleneck.
  • Auto-scaling matches capacity to demand — pay for the shape of demand, not the peak. Always set min/max limits and budget alerts.
  • Environments: Dev → Test → Staging → Production. Never build straight into production — a change earns its way up.

4 · Security & communications

  • Shared responsibility: the provider secures the cloud; you secure what's in it. Most breaches are on the customer side.
  • Identity: least privilege + MFA + roles, not shared logins.
  • Data: encrypt at rest (a locked safe) and in transit (an armoured van / the HTTPS padlock).
  • Network: a private network (VPC), only a public front door, firewalls, and segmentation so a breach can't spread.
  • Prove it: logging, monitoring, and compliance (India's DPDP Act, health-data rules).

5 · Storage — options, tiers & management

  • Types: object (warehouse of labelled boxes — files, images, backups), block (a hard-drive for one server — databases), file (a shared network drive).
  • Tiers: hot (frequent, dearest) → cool (infrequent) → archive (rare, cheapest, slow to retrieve). Tiering is the biggest storage-cost lever.
  • Manage: lifecycle rules auto-move ageing data to cheaper tiers; watch egress (getting data out can cost more than storing it); tag everything for cost control.

6 · Real-world anchors

Concrete examples you can bring into the debate — all widely reported:

  • Hybrid — banks & Zerodha: banks keep the core banking ledger on-prem for regulation and stability while apps and analytics run in cloud. India's largest broker, Zerodha, deliberately self-manages latency-sensitive systems rather than defaulting everything to cloud — "cloud-first" isn't "cloud-only".
  • Scaling — Hotstar & Flipkart: Disney+ Hotstar has streamed IPL cricket to tens of millions of concurrent viewers (among the highest ever recorded); Flipkart's "Big Billion Days" drives 10–50× normal traffic. Both pre-scale and rehearse for weeks — they don't rely on auto-scaling alone.
  • Security — Capital One (2019): a misconfiguration exposed personal data of ~100 million people. The provider wasn't hacked; the customer's configuration failed. This is the shared-responsibility lesson in one headline — and exactly the kind of slip you're checking for in Round 3.
  • Storage — Dropbox: at enormous scale, Dropbox built its own storage and moved most data off public cloud, reportedly saving ~$75M over two years. Cloud is usually cheaper to start — but at huge scale, storage economics can flip. Keep measuring.

Round 1 — reading the CAF readiness

PerspectiveModel ratingWhy
BusinessAd-hoc / DevelopingGrowth ambition exists, but no cloud business case or funding model — write one first.
PeopleAd-hocOnly two cloud engineers and anxious staff. This is usually the weakest — and hardest — gap.
GovernanceAd-hocNo tagging, no budget alerts, case-by-case compliance. Fix in a landing zone.
PlatformDevelopingSome cloud use but no landing zone or standard guardrails.
SecurityDevelopingEncryption on, but a public bucket and partial MFA drag it down (see Round 4).
OperationsDevelopingStrong for labs, patchy for cloud services.
Teaching point: the average lands around 2/4 — "not ready to scale, pilot only." The lowest scores are almost always People and Governance, which is the "~70% of cloud is people & governance" rule in action. The powerful insight: building a landing zone lifts Platform, Governance and Security at once (guardrails, tagging, budgets, encryption baked in) — so it's the highest-leverage first move. There's no single "right" set of ratings; reward teams who justify their scores and name a sensible first step.

Round 2 — model placement for each system

#SystemModelWhy
1Telehealth video appCloudSpiky demand needs elastic scale-out and global reach — the classic cloud fit.
2Lab diagnostic machinesOn-premPhysical analysers with local controllers must run on-site, even offline. Latency & hardware keep them local.

Teaching point: a real estate is a mix — cloud for elastic apps, on-prem for physical & latency-bound systems, hybrid to bridge the two. This mirrors how banks keep core banking on-prem while apps run in cloud, and how hospitals keep imaging on-site but run patient portals in cloud. Sensitive data can go to cloud with the right controls; the debate about #3 is the whole lesson. Good guardrails to mandate: encryption on, MFA for all, Indian-region data, least-privilege, tagging, budget alerts, central logging.

Round 4 — facilitating the decision

The model call is Block (or a very firm Approve-with-conditions that treats the bucket as a hard gate). The public scan-images bucket is a live patient-privacy breach and a likely DPDP violation — it must be closed before any launch. The two ambers (MFA at 90%, DPDP sign-off pending) are real but can be conditions with deadlines; the three greens are genuinely fine.

Debrief questions (pick 2–3)

  • Where did you keep something on-prem or hybrid that a pure-cloud purist would have moved — and were you right?
  • The storage saving was ~62% for the same data. Why do so many companies still leave everything hot?
  • One misconfiguration nearly shipped a breach. What process would stop that reaching a go-live at all?
  • Which of today's four areas — framework/hybrid, scaling, security, storage — is hardest to get right, and why?
Reference

Quick glossary

CAF
Cloud Adoption Framework — a governed, company-wide playbook for using cloud well.
Landing zone
A pre-secured, pre-governed area of cloud, set up before workloads move in.
Hybrid
Running some systems on-prem and some in cloud, joined securely as one.
Scale up / out
Make one server bigger vs. add more servers to share the load.
Auto-scaling
Capacity that grows and shrinks automatically with demand.
Environments
Separate copies — Dev, Test, Staging, Production — so changes are proven before going live.
Shared responsibility
Provider secures the cloud; you secure what you put in it.
IAM / least privilege
Identity & access management; grant the minimum access needed, no more.
MFA
Multi-factor authentication — a password plus a second proof.
Encryption at rest / in transit
Scrambling stored data / data moving over the network.
VPC
Your own private, walled-off network inside the cloud.
Object / block / file
Storage for files & images / server disks / shared network drives.
Hot / cool / archive
Storage tiers from frequent-and-dear to rare-cheap-and-slow.
Lifecycle rule
Automatic policy that moves ageing data to cheaper tiers.
Egress
Data-transfer-out fees — getting data out can cost more than storing it.
DPDP Act
India's Digital Personal Data Protection Act (2023) governing personal data.
Storage cost = Σ (TB × 1000 × ₹/GB) per tier  ·  Saving = all-hot cost − your tiered cost  ·  match tier to access frequency
